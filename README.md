# Zyke

Zyke was an AI marketing agent built at IIT Kharagpur in 2024. It learned a brand's voice, tracked what was trending, and turned both into finished social posts with AI-generated images that could be edited by clicking on them. The company wound down in 2025.

This repository is the home for everything that is left of it:

- **`main`** — the current site at [zyke.in](https://zyke.in): a static page that explains what Zyke was, what it did, how it worked, with the product demo video. Built with Next.js 14 and exported as plain HTML.
- **Legacy branches** — the older codebases, kept intact with their full git history:

| Branch | What it is | Dates | Notes |
|---|---|---|---|
| `legacy/zyke-frontend-app` | The version 1.0 Next.js web app (auth, brand voice wizard, idea generator, post generation, click-to-segment editing, Razorpay credits) plus its DOC.md | Oct 2024 – Aug 2025 | This is what `main` looked like before the site was rebuilt. Identical to the former `rupammahato/zyke-new-2` repo plus two documentation commits. |
| `legacy/zyke` | The original July 2024 product: one Flask route and a hand-written HTML/JS page with a five-stage prompt chain | Jul – Oct 2024 | Was `Tasmay-Tibrewal/Zyke`. Its backend ran at flask.app.zyke.in. |
| `legacy/zyke-vercel` | A standalone one-page marketing site made for Vercel | Oct 2024 | Was `rupammahato/zyke-vercel`. |

Repos that were **not** brought in, because they are strict subsets of a branch above:

- `zyke-new-2` is the first 32 commits of `legacy/zyke-frontend-app` (same commit hashes).
- `zyke-new` is `zyke-new-2` before its history was rewritten to remove a committed `.env`. It is deliberately not pushed here because it contains real secrets.
- `Zyke-Team` is a byte-identical copy of three snapshots of `legacy/zyke`.
- `zyke-backend` (the Flask + MongoDB API behind the app) is a separate repository at `rupammahato/zyke-backend`.

## Working on the site

```bash
npm install
npm run dev        # http://localhost:3000
npm run build      # writes the static site to ./out
```

All copy and data for the page is in `lib/content.ts`. Sections are in `components/landing/`. Images under `public/posts`, `public/generated` and `public/masks` were generated by Zyke during the demo run.

## Root of the site

The static export lands in `out/` and everything a host needs is at its root:

| File | Why |
|---|---|
| `index.html`, `404.html` | the page, and a 404 for unknown paths |
| `.nojekyll` | stops GitHub Pages running Jekyll, which would drop `_next/` |
| `CNAME` | tells GitHub Pages the custom domain is `zyke.in` |
| `robots.txt` | allows every crawler, search and AI alike, and points at the sitemap |
| `sitemap.xml` | one URL, since the site is one page |
| `llms.txt` | the whole site as plain markdown, for agents and researchers |
| `site.webmanifest` | name, colours and icons |
| `favicon.ico`, `favicon.png`, `icon-192.png`, `icon-512.png`, `apple-touch-icon.png` | icons |

They live in `public/` and Next copies them verbatim. `next.config.mjs` sets
`output: "export"`, `trailingSlash: true` and `images: { unoptimized: true }`,
which is what makes a plain static host work.

## The Google tag

`app/layout.tsx` emits a GA4 tag, a Tag Manager container and a Search Console
verification meta tag, each only if its id is set at build time. Nothing is
injected otherwise, so the repo ships no tracking by default.

Locally, copy `.env.example` to `.env.local` and fill in what you have. In CI,
add them as Actions **variables** named `GA_ID`, `GTM_ID` and
`GOOGLE_SITE_VERIFICATION`; the workflow maps them to the `NEXT_PUBLIC_*` names.
They are build-time values baked into the HTML, which is unavoidable for a
static site and fine, because a GA measurement id is public anyway.

The page also carries JSON-LD describing the organisation, the founders and the
demo video, so search engines get the facts without parsing prose.

## Deploying

The site is a static export with no server, no API routes and no environment
needed at runtime. Any static host works. GitHub Pages is the obvious choice
since the repo is already there and the domain is yours.

### GitHub Pages, which is what this repo is set up for

1. Add the deploy workflow. It ships as `deploy/github-pages-workflow.yml` and
   belongs at `.github/workflows/deploy-pages.yml`. It is parked rather than
   installed because a token without the `workflow` scope cannot push any
   branch that touches `.github/workflows/`, so the file cannot reach the remote
   from here. Copy it into place through the GitHub web editor, or from a shell
   with a `workflow`-scoped token or SSH. `deploy/README.md` has both recipes.
   Once it exists it builds and publishes `out/` on every push to `main`.
2. In the repo, **Settings → Pages → Source: GitHub Actions**.
3. In **Settings → Pages → Custom domain**, enter `zyke.in` and save. Tick
   **Enforce HTTPS** once the certificate is issued, which takes a few minutes
   to an hour.
4. Set DNS as below.

### DNS for zyke.in

The domain is currently blank, so add these at your registrar. Apex plus `www`,
which is what GitHub Pages wants:

```
Type   Name   Value                  TTL
A      @      185.199.108.153        3600
A      @      185.199.109.153        3600
A      @      185.199.110.153        3600
A      @      185.199.111.153        3600
CNAME  www    zykelabs.github.io.    3600
```

All four A records, not one. If your registrar also offers AAAA and you want
IPv6, add `2606:50c0:8000::153`, `2606:50c0:8001::153`, `2606:50c0:8002::153`
and `2606:50c0:8003::153` on `@`.

Notes:

- `@` means the bare domain. Some registrars call it blank, or `zyke.in.`
- Delete any parked or forwarding record the registrar added, and any old A
  record pointing at the dead AWS box, or the apex will keep resolving there.
- Propagation is usually minutes, up to a day at worst. Check with
  `dig +short zyke.in` and `dig +short www.zyke.in`.
- GitHub issues the TLS certificate itself once DNS resolves. Do not tick
  Enforce HTTPS before then or it will error.

### Vercel instead

Also fine, and slightly less setup. Import the repo, framework Next.js, accept
the defaults, add `zyke.in` under the project's Domains, then follow the records
Vercel shows you: an `A` on `@` to `76.76.21.21` and a `CNAME` on `www` to
`cname.vercel-dns.com`. Vercel handles TLS. You do not need the export config
or the workflow on Vercel, but leaving them in place does no harm.

There is no reason to prefer one over the other here. The page is static, so
Pages costs nothing and keeps everything in one place; Vercel gives you instant
rollbacks and preview URLs per branch. Pages is the smaller moving part.

### Anywhere else

`npm run build` then serve `out/` from Cloudflare Pages, Netlify, S3 with
CloudFront, or any web server. The only requirement is that `.nojekyll` and
`CNAME` survive, and that unknown paths serve `404.html`.
